# Current Project Structure

This document explains how the simulator currently works.

The project is now a small event-driven market microstructure simulator. It can:

- Accept limit orders, market orders, and cancellations.
- Maintain a price-time-priority limit order book.
- Match orders and create trades.
- Track live resting liquidity.
- Assign order IDs and timestamps.
- Record trades, results, and book snapshots.
- Run deterministic event sequences.
- Let simple agents observe the market and emit events.

The next major direction is synthetic order flow and smarter agents, but the current foundation is already organized into clear layers.

## Dashboard Flow View

The `dashboard/` folder is a static educational visualization of the simulator.
It is not a separate market model. Its data comes from `dashboard/trace.json`,
which is generated by `examples/dashboard_trace.py`.

The trace generator runs the real Python `Simulation` and exports a deterministic
synthetic order stream:

```text
24 generic random agents
260 order events
two-sided book with smaller best-price levels
limit orders that add resting liquidity
market orders that consume liquidity
crossing limits that behave like limited liquidity-taking orders
book snapshots after every event
trade records when matching happens
midprice history for the chart
```

The dashboard animates the current event plus a short queue of recent events
through the same conceptual pipeline:

```text
Agent intent
    -> MarketEvent
    -> Exchange gateway validation and ID assignment
    -> MatchingEngine
    -> OrderBook mutation
    -> Recorder observation
    -> Midprice chart
```

Important implementation detail:

```text
Every visible connector is attached to a real DOM port.
```

The ports are small elements marked with `data-port`, for example
`data-port="matcher-out"` or `data-port="book-record"`. `dashboard/app.js`
measures those port positions in the browser and draws SVG lines between them.
This keeps the visual flow tied to the actual panels instead of using decorative
fixed lines.

The recorder receives two observer flows during the recorder phase:

```text
MatchingEngine -> Recorder:
    MatchResult / trade result

OrderBook -> Recorder:
    BookSnapshot / top-of-book and depth state
```

That distinction matters because a trade result tells us what happened to one
incoming order, while a book snapshot tells us what the market state looks like
after that event.

Each incoming order also receives a visual color based on its `order_id`. The
dashboard keeps the component boxes neutral and applies that color only to the
moving flow identity:

```text
short data-flow trail segments
short observer-flow trail segments
moving packet dots sized by order quantity
legend line samples
```

This is only a visual aid. It does not change simulator behavior. The goal is
to make it easier to distinguish one fast incoming order from another without
making the whole interface change color. The static connector lines show the
system wiring; the colored dots and short trail segments show which order is
currently traveling through each part of the pipeline.

## High-Level Architecture

The system is layered:

```text
Agents / Fixed Events
        |
        v
Simulation
        |
        v
Exchange
        |
        v
MatchingEngine
        |
        v
OrderBook

Recorder observes results and book state after events.
```

Each layer has a narrow job:

```text
domain.py:
    Defines the basic market objects and result receipts.

book.py:
    Stores live resting liquidity.

matching.py:
    Applies matching rules and creates trades.

exchange.py:
    Assigns order IDs and timestamps.

recording.py:
    Records results, trades, and book snapshots.

simulation.py:
    Orchestrates event processing.

agents.py:
    Defines how agents observe and emit events.
```

## `domain.py`

`domain.py` contains the core market vocabulary.

### `Side`

```text
BUY
SELL
```

This tells us the economic side of an order or aggressor.

### `OrderType`

```text
LIMIT
MARKET
```

This tells us whether the order has price protection.

### `TimeInForce`

```text
GTC
IOC
FOK
```

This tells us what happens to unfilled quantity.

```text
GTC:
    Good-till-canceled. Leftover quantity can rest.

IOC:
    Immediate-or-cancel. Fill now, cancel leftover.

FOK:
    Fill-or-kill. Fill everything immediately or cancel everything.
```

### `Order`

`Order` is the official exchange instruction after ID and timestamp assignment.

It stores:

```text
order_id
side
order_type
quantity
timestamp
price_ticks
time_in_force
```

Important idea:

```text
Order is historical input.
It does not mutate after creation.
```

For example, if an order was submitted for `25_000` sats, the `Order.quantity` remains `25_000` even after partial fills.

### `Trade`

`Trade` records one execution.

It stores:

```text
trade_id
price_ticks
quantity
buyer_order_id
seller_order_id
aggressor_order_id
resting_order_id
aggressor_side
timestamp
```

This gives both economic roles and microstructure roles:

```text
buyer/seller:
    Who bought and who sold?

aggressor/resting:
    Who took liquidity and who provided liquidity?
```

### `MatchResult`

`MatchResult` is the receipt returned after one incoming order is processed.

It stores:

```text
incoming_order_id
timestamp
trades
filled_quantity
canceled_quantity
resting_quantity
resting_order_id
```

This lets the rest of the simulator know exactly what happened to the incoming order.

### `CancelResult`

`CancelResult` is the receipt returned after one cancel attempt.

It stores:

```text
order_id
accepted
canceled_quantity
timestamp
```

If the order was live, `accepted=True`. If not found, `accepted=False`.

## `book.py`

`book.py` stores live resting liquidity.

The key distinction:

```text
Order:
    Original submitted instruction.

BookOrder:
    Live/open state currently resting in the book.
```

### `BookOrder`

`BookOrder` stores:

```text
order_id
side
price_ticks
remaining_quantity
timestamp
```

`remaining_quantity` can change after partial fills. When it reaches zero, the book removes the `BookOrder`.

### `PriceLevel`

`PriceLevel` represents all live orders at one price.

Internally it uses:

```python
deque[BookOrder]
```

The `deque` is a FIFO queue:

```text
new orders append to the back
oldest orders stay at the front
matching consumes from the front
```

That models time priority at the same price.

### `OrderBook`

The book stores bids and asks separately:

```text
bids: price_ticks -> PriceLevel
asks: price_ticks -> PriceLevel
```

Bids and asks sort differently:

```text
bids:
    highest price is best

asks:
    lowest price is best
```

The book can answer:

```text
best_bid
best_ask
spread
mid_price
depth_at(side, price)
orders_at(side, price)
price_levels(side)
```

It also exposes methods used by matching:

```text
best_price_for_side(side)
best_level_for_side(side)
peek_best_order(side)
remove_best_order(side)
```

### Cancellation Index

The book also maintains:

```python
orders_by_id: dict[int, BookOrderLocation]
```

The main book structure is optimized for matching:

```text
side -> price -> FIFO queue
```

The index is optimized for cancellation:

```text
order_id -> side and price level
```

Full cancellation flow:

```text
1. Look up order_id in orders_by_id.
2. Jump to the correct side and price level.
3. Remove the BookOrder from that level's queue.
4. Remove the price level if empty.
5. Remove the ID from orders_by_id.
```

## `matching.py`

`matching.py` contains `MatchingEngine`.

The matching engine owns execution rules. It does not store liquidity itself.

### Main Method

```python
process_order(order) -> MatchResult
```

It receives one official `Order`, interacts with the `OrderBook`, creates `Trade` objects, and returns a `MatchResult`.

### Core Matching Logic

For an incoming buy order:

```text
opposite side = SELL
look at best ask
```

For an incoming sell order:

```text
opposite side = BUY
look at best bid
```

Loop:

```text
incoming_remaining = order.quantity

while incoming_remaining > 0:
    resting = book.peek_best_order(opposite_side)

    if no resting order:
        stop

    if incoming order cannot cross resting price:
        stop

    trade_quantity = min(incoming_remaining, resting.remaining_quantity)

    create Trade

    incoming_remaining -= trade_quantity
    resting.remaining_quantity -= trade_quantity

    if resting.remaining_quantity == 0:
        book.remove_best_order(opposite_side)
```

### Crossing Rules

Market orders:

```text
cross any available opposite-side liquidity
```

Buy limit orders:

```text
can trade if limit price >= resting ask
```

Sell limit orders:

```text
can trade if limit price <= resting bid
```

### Leftover Rules

After matching:

```text
GTC limit leftover:
    rests in the book

IOC leftover:
    canceled

Market order leftover:
    canceled

FOK:
    pre-checks full fill availability
```

FOK is special because it must not partially mutate the book if the full order cannot fill.

## `exchange.py`

`exchange.py` contains `Exchange`.

The exchange is the boundary where intent becomes official market messages.

It owns:

```text
book
matching engine
next_order_id
next_timestamp
```

### Why IDs Live Here

`Order` stores an assigned ID, but does not generate it.

Reason:

```text
Order:
    validated instruction

Exchange:
    official market boundary that assigns identity and event time
```

### Main Methods

```python
submit_limit_order(side, quantity, price_ticks, time_in_force)
submit_market_order(side, quantity)
cancel_order(order_id)
```

Submitting a limit order:

```text
1. Take next order_id.
2. Take next timestamp.
3. Build Order.
4. Send Order to MatchingEngine.
5. Return MatchResult.
```

Canceling:

```text
1. Take next timestamp.
2. Call book.cancel_order(order_id).
3. Wrap result into CancelResult.
```

## `recording.py`

`recording.py` contains historical recording tools.

### `BookSnapshot`

`BookSnapshot` freezes the book state at one timestamp.

It stores:

```text
timestamp
best_bid
best_ask
spread
mid_price
bid_depth
ask_depth
```

Depth is stored as immutable tuples:

```text
((price_ticks, quantity), ...)
```

This matters because the live book keeps changing. Old snapshots should not change.

### `Recorder`

`Recorder` stores:

```text
match_results
cancel_results
trades
snapshots
```

Recording a match:

```text
1. Store MatchResult.
2. Store every Trade from the result.
3. Store post-event BookSnapshot.
```

Recording a cancel:

```text
1. Store CancelResult.
2. Store post-event BookSnapshot.
```

The recorder is separate from `Exchange`:

```text
Exchange changes market state.
Recorder observes and stores history.
```

## `simulation.py`

`simulation.py` contains the event orchestrator.

### Event Types

These are intent events:

```text
SubmitLimitOrder
SubmitMarketOrder
CancelOrder
```

They are not official `Order` objects because they do not yet have IDs or timestamps.

### `Simulation`

`Simulation` owns:

```text
exchange
recorder
```

It coordinates:

```text
MarketEvent
    -> Exchange
    -> MatchingEngine / OrderBook
    -> Recorder
```

### Fixed Event Runs

```python
simulation.run(events, max_events=None)
```

This processes a finite sequence of events.

### Single Event Processing

```python
simulation.process_event(event)
```

This processes one event and records the result.

This method is important because agents and synthetic data sources can use the same path later.

### Agent Steps

```python
simulation.run_agent_steps([agent], max_steps=10)
```

Each step:

```text
1. Create current BookSnapshot observation.
2. Ask each agent for actions.
3. Process emitted actions.
4. Record results and post-event snapshots.
```

### `SimulationResult`

The run summary stores:

```text
processed_events
match_results
cancel_results
trades
snapshots
```

## `agents.py`

`agents.py` defines agent behavior.

### `Agent`

`Agent` is a protocol:

```python
decide(observation: BookSnapshot) -> list[MarketEvent]
```

Agents observe the market and return intent events.

They do not directly mutate:

```text
OrderBook
MatchingEngine
Exchange
Recorder
```

### `ScriptedAgent`

`ScriptedAgent` is the first test agent.

It:

```text
1. Receives a BookSnapshot.
2. Saves that observation.
3. Emits the next predefined event.
```

It is not a strategy. It exists to prove the agent/simulation interface before adding real market-making logic.

## Main Data Flows

### Resting Limit Order

Example:

```text
SubmitLimitOrder(SELL, 25_000, 10_010)
```

Flow:

```text
Simulation
    receives SubmitLimitOrder

Exchange
    assigns order_id = 1
    assigns timestamp = 1
    creates Order

MatchingEngine
    checks opposite side
    finds no crossing bid
    leaves quantity unfilled

OrderBook
    converts Order into BookOrder
    stores BookOrder on ask side at 10_010

Recorder
    stores MatchResult
    stores BookSnapshot
```

### Market Order

Example:

```text
SubmitMarketOrder(BUY, 10_000)
```

Flow:

```text
Exchange
    creates buy market Order

MatchingEngine
    looks at ask side
    peeks best ask
    creates Trade
    reduces BookOrder.remaining_quantity

OrderBook
    removes BookOrder if fully filled

Recorder
    stores MatchResult
    stores Trade
    stores post-event snapshot
```

### Cancellation

Example:

```text
CancelOrder(order_id=1)
```

Flow:

```text
Simulation
    receives CancelOrder

Exchange
    assigns cancel timestamp
    calls book.cancel_order(1)

OrderBook
    looks up order_id in orders_by_id
    removes BookOrder from its PriceLevel queue
    deletes empty price level if needed

Exchange
    returns CancelResult

Recorder
    stores CancelResult
    stores post-event snapshot
```

### Agent Step

Flow:

```text
Simulation
    creates BookSnapshot from current book

Agent
    observes BookSnapshot
    returns one or more MarketEvents

Simulation
    processes each emitted MarketEvent normally
```

## Current Limitations

The simulator does not yet have:

- Synthetic random order flow.
- Real market-maker strategy.
- Portfolio, cash, inventory, or PnL.
- Fees, tick-size validation, lot-size validation, or minimum notional checks.
- Latency or queue-position modeling beyond FIFO.
- Real exchange data replay.
- Automatic package install workflow.

The next natural direction is synthetic data/event generation, then a basic market-maker agent.
